# Migration Guide: sign-in through a social provider, with an optional silent attempt

The login page offers one button per social provider the API lists in `GET /iam/features` (`socialProviders`), for
example Microsoft Entra ID as single sign-on. With `NG_PUBLIC_AUTH_SILENT_PROVIDER=<id>` it tries once per tab to sign
in without interaction (`prompt=none`) and renders "Anmeldung wird geprüft …" from the server on, until it knows
whether the attempt runs. The new page `/auth/callback` finishes the sign-in. Same behaviour as the Nuxt template
(nuxt-base-starter #58); the rules are rule 13 of "Authentication rules" in `CLAUDE.md`.

| Project                                                   | What to do                                                              |
| --------------------------------------------------------- | ----------------------------------------------------------------------- |
| Wants sign-in through a provider                          | Steps 1-6, then configure the API (step 7)                              |
| Does not want it                                          | Nothing; the starter's pages work unchanged                             |
| Takes the starter's auth pages over anyway (later merges) | Steps 1-6; without a provider in the API the login page looks as before |

The API decides which providers exist: without `betterAuth.socialProviders` in nest-server the login page shows no
provider button and the silent attempt never runs, whatever the app is set to.

## Upgrade steps (existing project)

In an `lt fullstack` monorepo, the steps happen in `projects/app/`.

### 1. ng-base with `signIn.social`

Pin `@lenne.tech/ng-base` 22.1.2 or later: it brings `LtAuthService.signIn.social()` and keeps inline profile photos
out of the auth state. A vendored core takes that release over with
`/lt-dev:frontend:update-ng-base-core`.

### 2. Take over the new files

Copy from the starter into `src/app/auth/`, each with its `.spec.ts`:

- `social-providers.ts`: button label and icon per provider, the provider of the silent attempt;
- `social-sign-in-marks.ts`: the "attempted" (`sessionStorage`) and "signed out" (`localStorage`) marks;
- `social-sign-in-error.ts`: the German texts for `?error=` and the URL cleaning;
- `sign-in-error-text-guard.ts`: removes `error_description` from the login URL before rendering (302 on the server);
- `callback-page.ts` and `callback-page.html`: `/auth/callback`.

### 3. Routes

In `src/app/app.routes.ts`, the login route gets the guard after `guestGuard`, and `/auth/callback` is new (no
`ltAuthGuard`: the user is not loaded yet):

```ts
{
  path: 'login',
  canActivate: [guestGuard, signInErrorTextGuard],
  loadComponent: () => import('./auth/login-page').then((m) => m.LoginPage),
  title: 'Anmeldung',
},
{ path: 'callback', loadComponent: () => import('./auth/callback-page').then((m) => m.CallbackPage), title: 'Anmeldung' },
```

### 4. Login page, 2FA page, sign-out

- Copy `src/app/auth/login-page.ts`, `login-page.html` and `login-page.spec.ts`, or merge: the provider buttons in the
  footer before the passkey button, the `lt-notice` for `socialError()`, the status line and `[attr.hidden]` on the
  card, the silent attempt, the `pageshow` handler, and `this.marks.clear()` after a password or passkey sign-in.
- `src/app/auth/two-factor-page.ts`: `this.marks.clear()` before the navigation after an accepted code.
- Every sign-out (`src/app/layout/default-layout.ts`, `src/app/dashboard/dashboard-page.ts` and your own) calls
  `this.marks.markSignedOut()` before `auth.signOut()`, with `private readonly marks = injectSocialSignInMarks();`.

### 5. Runtime value

`src/server/starter-runtime-config.ts` returns `authSilentProvider` from `NG_PUBLIC_AUTH_SILENT_PROVIDER` next to
`plausibleApiHost` (copy the file and its cases in `tests/unit/server/server-helpers.test.ts`). Add the variable,
empty, to `.env.example` and to the stages that should sign in silently.

### 6. Contract tests

- Copy `tests/unit/auth/sign-out-marks.test.ts`: it fails for a sign-out that does not set the mark.
- `tests/unit/auth/auth-pages-translate-errors.test.ts` exempts `callback-page`, which shows no backend error.
- Optional: `tests/e2e/auth-social-sign-in.spec.ts` and its section in `docs/e2e-auth.md`.

### 7. The API

Configure the provider in nest-server under `betterAuth.socialProviders.<id>` (for Microsoft Entra ID: `microsoft`
with client id, client secret, tenant id and `disableProfilePhoto: true`) and register `<API URL>/iam/callback/<id>`
as the redirect URI at the provider. The app origin must be in the API's `trustedOrigins`, as for the reset links.

The tenant id needs nest-server 12.10.0 or later. Older versions hand Better Auth only `clientId`, `clientSecret` and
`disableSignUp` and drop every other provider option without a warning: without `tenantId` Microsoft signs in accounts
of every organization and personal Microsoft accounts (tenant `common`). A project that closes e-mail sign-up and opens
it for Microsoft alone would then give an account to anyone with a Microsoft login. Upgrade the API first. Take
12.10.1, the security release on top of 12.10.0.

## Check it

`pnpm test` runs the new specs. In the browser, with a provider configured in the API: the login page shows "Mit
<Name> anmelden"; `/auth/login?error=access_denied&error_description=Text` answers with a 302 to the URL without
`error_description` and shows "Kein Zugang". With `NG_PUBLIC_AUTH_SILENT_PROVIDER` set, a tab with a provider session
lands in the app without a click; after "Abmelden" the login form stays.
