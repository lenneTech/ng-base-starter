# Migration Guide: the other pages follow `/iam/features` too

The login page offers only the sign-in methods `GET /iam/features` reports (`22.1.4-sign-in-methods-from-features.md`).
An API that signs in through social providers alone (`betterAuth.emailAndPassword.enabled: false`, nest-server 12.11.0+)
still met four places that assumed a password:

- `/app/settings/security` offered "2FA aktivieren" and "Passkey hinzufügen". The API reports `twoFactor: false` and
  `passkey: false` there, the endpoints answer 404, and every click failed. The page also asked for the passkey list on
  every visit and logged the 404.
- `/auth/forgot-password` showed its form. There is no password to reset, and the request fails.
- `?error=account_not_linked` after a provider sign-in asked to sign in "wie bisher", which pointed at a password nobody
  can use there.
- `/auth/setup` created the first admin with a password without saying how that admin signs in.

Same behaviour as the Nuxt template (nuxt-base-starter 4.0.7); the rule is rule 12 of "Authentication rules" in
`CLAUDE.md`.

| Page                        | With `false`                                                                                                         |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `/app/settings/security`    | `twoFactor`: no 2FA section; `passkey`: no passkey section and no list request; neither left: a hint                 |
| `/auth/forgot-password`     | `emailAndPassword`: to the login with the toast "Passwort zurücksetzen nicht verfügbar", replacing the history entry |
| `?error=account_not_linked` | `emailAndPassword`: points at the provider used before or the administration                                         |
| `/auth/setup`               | `emailAndPassword`: the form stays, with a hint how the admin signs in                                               |

Only an explicit `false` changes a page: an API before 12.11.0 does not report the fields, and everything stays as it
was. The security page, the forgot-password page and the setup page fetch the features during SSR, so the server HTML
already shows the right state.

**The first admin of a provider-only API.** `POST /system-setup/init` still wants a password. The admin signs in through
a provider whose account carries the same address, and Better Auth 1.7 links that account to the admin on the first
sign-in only when the provider reports the address as verified, and the admin's own address is verified (the system
setup sets it). GitHub reports the verified flag of the address. Microsoft Entra ID reports it only with the optional
ID token claim `verified_primary_email`: add it in the app registration under "Token configuration" → "Add optional
claim" → ID. Without it the admin's first sign-in ends with `account_not_linked`.

Do not list the provider in `betterAuth.options.account.accountLinking.trustedProviders` to get there. It skips the
provider's check: Better Auth then links whatever address the provider names, verified or not, and an Entra tenant admin
who sets a user's `mail` to the admin's address signs in as the admin ("nOAuth"; Microsoft warns about apps that
identify users by the e-mail claim). `emailVerified: true` from a provider's `mapProfileToUser` opens the same gap: Better Auth spreads
that result over the provider's own check (`microsoft-entra-id.mjs`, better-auth 1.7).

The password the setup asks for is a dormant credential: it does nothing while e-mail and password are off, and signs
the admin in once they are switched on. Take a long random value and do not keep it.

| Project                                                                 | What to do                        |
| ----------------------------------------------------------------------- | --------------------------------- |
| Signs in through providers alone, or will (API on nest-server 12.11.0+) | Steps 1 to 4, then 5              |
| Has 2FA or passkeys switched off in the API                             | Step 1                            |
| Any other                                                               | Nothing; the steps change nothing |

No dependency changes; it works with every ng-base 22.1.x.

## Upgrade steps (existing project)

In an `lt fullstack` monorepo, the steps happen in `projects/app/`. Where a file is still the starter's, take it over;
otherwise apply the changes by hand.

### 1. `src/app/settings/security-page.ts` and `security-page.html`

```ts
/** Two-factor authentication, unless the API reports it off. */
protected readonly twoFactorAvailable = computed(() => this.auth.features()['twoFactor'] !== false);
/** Passkeys, unless the API reports them off. */
protected readonly passkeyAvailable = computed(() => this.auth.features()['passkey'] !== false);
/** Sign-in through providers alone: the provider's account holds the second factor, not this one. */
protected readonly providersOnly = computed(() => this.auth.features()['emailAndPassword'] === false);

constructor() {
  void this.auth.fetchFeatures();
  afterNextRender(() => void this.loadPasskeysIfKept());
}

/** The passkey list once the features are known; without passkeys on the API the request answers 404. */
private async loadPasskeysIfKept(): Promise<void> {
  try {
    await this.auth.fetchFeatures();
  } catch {
    // The last known features decide.
  }
  if (this.passkeyAvailable()) {
    await this.loadPasskeys();
  }
}
```

In the template, the 2FA section goes into `@if (twoFactorAvailable()) { … }` and the passkey section into
`@if (passkeyAvailable()) { … }`. Above them, inside `@if (!twoFactorAvailable() && !passkeyAvailable()) { … }`, a
`<lt-notice variant="neutral" title="Keine weiteren Anmeldefaktoren">` says, with `providersOnly()`:

> Du meldest dich über einen externen Anbieter an. Zwei-Faktor-Authentifizierung und weitere Schutzmaßnahmen richtest
> du in deinem Konto bei diesem Anbieter ein.

and otherwise:

> Zwei-Faktor-Authentifizierung und Passkeys sind für diese Anwendung nicht eingerichtet.

### 2. `src/app/auth/forgot-password-page.ts`

Inject `Router`, `LtToastService` and `PLATFORM_ID`, and add to the constructor, after `fetchFeatures()`:

```ts
let leaving = false;
effect(() => {
  if (!this.isBrowser || leaving || this.auth.features()['emailAndPassword'] !== false) {
    return;
  }
  leaving = true;
  this.toast.show({
    color: 'warning',
    description: 'Diese Anwendung nutzt keine Anmeldung mit Passwort. Bitte melde dich über die Anmeldeseite an.',
    title: 'Passwort zurücksetzen nicht verfügbar',
  });
  void this.router.navigateByUrl('/auth/login', { replaceUrl: true });
});
```

As on the register page: in the browser only (a server redirect is a bare 302 and would lose the toast), once (the
browser's own answer is a new object and would show a second toast), and replacing the history entry ("Zurück" must
not land on the page that sends the visitor away again).

### 3. `src/app/auth/social-sign-in-error.ts` and `login-page.ts`

`socialSignInError(code, context)` takes a second argument, `{ passwordSignIn?: boolean }`, and returns for
`account_not_linked` with `passwordSignIn: false`:

> Für diese E-Mail-Adresse gibt es bereits ein Konto, das nicht mit diesem Anbieter verbunden ist. Bitte melde dich über
> den Anbieter an, den du bisher genutzt hast, oder wende dich an die Administration.

Every other code and every other call keeps its text. On the login page the code goes into a signal and the message is
computed from it, so it follows the features:

```ts
private readonly socialErrorCode = signal<unknown>(this.arrivedQuery['error']);
protected readonly socialError = computed(() => socialSignInError(this.socialErrorCode(), { passwordSignIn: this.passwordSignIn() }));
```

Every `this.socialError.set(null)` becomes `this.socialErrorCode.set(null)`.

### 4. `src/app/auth/setup-page.ts` and `setup-page.html`

```ts
private readonly auth = inject(LtAuthStore); // from '@lenne.tech/ng-base/auth/provide', the light entry
protected readonly providersOnly = computed(() => this.auth.features()['emailAndPassword'] === false);
// in the constructor:
void this.auth.fetchFeatures();
```

In the `form` view, after the heading block:

```html
@if (providersOnly()) {
<lt-notice variant="info" title="Anmeldung nur über einen Anbieter" class="mb-6">
  <div class="space-y-2 text-sm">
    <p>Gib die E-Mail-Adresse an, die das Konto des Administrators beim Anbieter hat. Das Passwort verlangt die Einrichtung, zum Anmelden dient es nicht.</p>
    <p class="wrap-anywhere">
      Die API verbindet beide Konten bei der ersten Anmeldung, wenn der Anbieter die Adresse als bestätigt meldet. GitHub tut das, Microsoft Entra ID mit dem optionalen Claim
      <code>verified_primary_email</code> in der App-Registrierung.
    </p>
  </div>
</lt-notice>
}
```

A spec of your own that renders the page needs `LtAuthStore` in its providers (`{ features: signal({}), fetchFeatures }`).

### 5. Optional: the tests

- `src/app/settings/security-page.spec.ts` and `src/app/auth/forgot-password-page.spec.ts`: new, copy them.
- `src/app/auth/setup-page.spec.ts`, `login-page.spec.ts` and `social-sign-in-error.spec.ts`: take over the provider-only
  cases. The setup spec fails when the hint names `trustedProviders`.
- `tests/e2e/auth-sign-in-methods.spec.ts`: the new test for `/auth/forgot-password` runs with
  `E2E_SIGN_IN_CASE=providers-only` against an API that signs in through a provider alone (`docs/e2e-auth.md`).

## Check it

```bash
pnpm run check
```

With the API signing in through a provider alone: `/auth/forgot-password` goes to the login with "Passwort zurücksetzen
nicht verfügbar", `/auth/setup` on an empty database shows the hint above the form, and a signed-in user sees only
"Kontoinformationen" and the hint on `/app/settings/security`.
