# Migration Guide: the login page offers the sign-in methods `/iam/features` reports

From nest-server 12.11.0 on, `GET /iam/features` reports `emailAndPassword`. It is `false` for an API that signs in
through social providers alone (`betterAuth.emailAndPassword.enabled: false`), and such an API then reports
`passkey: false` and `twoFactor: false` as well, unless it keeps a factor deliberately. Until now the login page showed
the e-mail and password form, "Passwort vergessen?", "Registrieren" and the passkey button whatever the API reported.
On a provider-only API every one of them leads to an error. Same behaviour as the Nuxt template (nuxt-base-starter
4.0.6); the rule is rule 12 of "Authentication rules" in `CLAUDE.md`.

The login page now follows the features:

- `emailAndPassword: false`: no form, no "Passwort vergessen?", no "Registrieren". `/auth/register` sends the visitor
  to the login with a toast; with sign-up open, the account comes with the first sign-in through a provider.
- `passkey: false`: no passkey button. This also holds for an older API with passkeys switched off, where the button
  could only fail.
- No method left at all: the hint "Anmeldung nicht möglich" instead of an empty card.

Only an explicit `false` takes a method away. An API before 12.11.0 does not report `emailAndPassword`, and the form
stays. The server already fetched `/iam/features` before it rendered the login page (`provideLtAuth()` waits for it,
and the browser starts with the server's answer), so the server HTML shows the right methods and nothing appears or
disappears after load.

| Project                                                                 | What to do                  |
| ----------------------------------------------------------------------- | --------------------------- |
| Signs in through providers alone, or will (API on nest-server 12.11.0+) | Steps 1 and 2, then 3       |
| Has passkeys switched off in the API                                    | Step 1                      |
| Wants the unit and E2E checks                                           | Step 3, optional            |
| Any other                                                               | Nothing; step 1 if you like |

No dependency changes; it works with every ng-base 22.1.x.

## Upgrade steps (existing project)

In an `lt fullstack` monorepo, the steps happen in `projects/app/`.

### 1. `src/app/auth/login-page.ts` and `login-page.html`

Take both files over if yours are the starter's. Otherwise apply the changes by hand. In the component:

```ts
protected readonly passwordSignIn = computed(() => this.auth.features()['emailAndPassword'] !== false);
protected readonly passkeySignIn = computed(() => this.auth.features()['passkey'] !== false);
protected readonly signUpEnabled = computed(() => this.passwordSignIn() && this.auth.features()['signUpEnabled'] !== false);

// after `socialButtons`:
protected readonly showSeparator = computed(() => this.passwordSignIn() && (this.passkeySignIn() || this.socialButtons().length > 0));
protected readonly noSignInMethod = computed(() => !this.passwordSignIn() && !this.passkeySignIn() && this.socialButtons().length === 0);
```

In the template:

- The `<form>` (fields, "Passwort vergessen?", submit button) goes into `@if (passwordSignIn()) { … }`.
- The "oder" separator into `@if (showSeparator()) { … }`.
- The passkey button into `@if (passkeySignIn()) { … }`.
- After it, the hint:

  ```html
  @if (noSignInMethod()) {
  <lt-notice variant="warning" title="Anmeldung nicht möglich">
    Für diese Anwendung ist derzeit keine Anmeldemethode eingerichtet. Bitte wende dich an die Betreiber der Anwendung.
  </lt-notice>
  }
  ```

`LtNotice` is in the page's `imports` already (it shows the `?error=` message).

### 2. `src/app/auth/register-page.ts`

The effect that sends the visitor to the login on `signUpEnabled === false` reacts to `emailAndPassword` too:

```ts
let leaving = false;
effect(() => {
  if (!this.isBrowser || leaving) {
    return;
  }
  const features = this.auth.features();
  const signUpClosed = features['signUpEnabled'] === false;
  if (signUpClosed || features['emailAndPassword'] === false) {
    leaving = true;
    this.toast.show({
      color: 'warning',
      description: signUpClosed
        ? 'Die Registrierung ist derzeit deaktiviert.'
        : 'Eine Registrierung mit E-Mail und Passwort ist hier nicht möglich. Bitte melde dich über die Anmeldeseite an.',
      title: 'Registrierung nicht verfügbar',
    });
    void this.router.navigateByUrl('/auth/login', { replaceUrl: true });
  }
});
```

Keep the redirect in the browser. A redirect from the server is a bare 302 without the page, and the toast would be
lost. `leaving` makes it happen once: the page starts with the server's answer, and the browser's own answer can
arrive while the login route still loads; without the flag the toast showed twice. `replaceUrl` keeps "Zurück" from landing on
`/auth/register` again, which would send the visitor away once more with another toast; this also holds for the older
case of sign-up closed.

### 3. Optional: the tests

- `src/app/auth/login-page.spec.ts` (describe "the sign-in methods /iam/features reports") and the new
  `src/app/auth/register-page.spec.ts`: take them over.
- `tests/e2e/auth-sign-in-methods.spec.ts`: copy it, and add `emailAndPassword: boolean` to `Features` and
  `emailAndPassword: true` to `DEFAULT_FEATURES` in `tests/e2e/helpers/auth-backend.ts`. Without the field
  `pnpm run typecheck:tests` fails with `TS2339`.

  Against an API as nest-server-starter ships it, the spec checks that the form stays. The provider-only case needs an
  API started with `NSC__BETTER_AUTH__EMAIL_AND_PASSWORD__ENABLED=false` and a provider
  (`NSC__BETTER_AUTH__SOCIAL_PROVIDERS__GITHUB__CLIENT_ID` and `__CLIENT_SECRET`, any value) and the spec run with
  `E2E_SIGN_IN_CASE=providers-only`. Without that variable, the provider-only checks skip. `docs/e2e-auth.md` and the
  `e2e-auth` job in `.github/workflows/test.yml` show the run.

## Check it

```bash
pnpm run check
```

With the API signing in through a provider alone, open `/auth/login`: only the provider buttons show, already with
JavaScript off. `/auth/register` goes to the login with "Registrierung nicht verfügbar".
