# Migration Guide: `check` survives a taken port; the E2E check for a session the API ended

Two changes to the project's tooling. Neither touches the app's runtime. Same as the Nuxt template (nuxt-base-starter
4.0.7, `4.0.7-server-start-retry-and-storage-prefix.md` and `4.0.7-redirect-after-ended-session.md`).

**`scripts/check-server-start.mjs` starts again after `EADDRINUSE`.** The last step of `check` binds a free port,
releases it and starts the built server on it. The port is free at that moment, not reserved: when another process (a
second `check`, a dev server, a test runner) binds it first, the server dies with `listen EADDRINUSE` and `check` went
red for a reason that has nothing to do with the project. Now the script starts the server again on newly allocated
ports, up to three times, and says why (`Port … was taken before the server bound it (EADDRINUSE), attempt 1 of 3`).
Only `EADDRINUSE` before the server is up counts; any other early exit fails at once, as before.

**`tests/e2e/auth-session-ended.spec.ts` checks what ng-base 22.1.4 fixed.** Since 22.1.4, `validateSession()` signs
out a cached user once `GET /iam/get-session` confirms that the API has no session for them; before, the app looked
signed in until the first protected request failed. The spec ends the session on the API, reloads `/app`, expects the
visitor signed out, and the next guarded page to ask for a sign-in and lead back. It is red with ng-base 22.1.3.

The Nuxt template's other 4.0.7 change, dropping `NUXT_PUBLIC_STORAGE_PREFIX`, does not apply here: ng-base's
`LtStorageService` reads `NG_PUBLIC_STORAGE_PREFIX`.

| Project                                                     | What to do       |
| ----------------------------------------------------------- | ---------------- |
| Runs `check` next to other servers or checks on one machine | Step 1           |
| Wants the E2E check, above all with an API without JWT      | Step 2, optional |

## Upgrade steps (existing project)

In an `lt fullstack` monorepo, the steps happen in `projects/app/`.

### 1. `scripts/check-server-start.mjs`

Take over `scripts/check-server-start.mjs` and `scripts/check-server-start.d.mts` from the starter, if yours are the
starter's. The options and the CLI arguments are unchanged; `NG_DEFAULTS` gains `portAttempts: 3`, and the module
exports `isPortTakenOutput()`.

The tests come with it: `tests/unit/check-server-start.test.ts` and the two fixtures
`tests/unit/fixtures/server-start/port-taken-once.mjs` and `port-always-taken.mjs`. The old test file stays green with
the new script, so they are optional.

### 2. Optional: `tests/e2e/auth-session-ended.spec.ts`

Copy the spec. It needs `tests/e2e/helpers/sign-in.ts` (`registerUser`), `Features.jwt` in
`tests/e2e/helpers/auth-backend.ts`, the API log for the verification token (`docs/e2e-auth.md`), and a guarded page
linked from `/app` (the starter's dashboard links "Sicherheit"; adapt the link and the `redirect` value otherwise).

- Cookie mode only: with `E2E_EXPECT_AUTH_MODE=jwt` it skips.
- Against an API without JWT (`NSC__BETTER_AUTH__JWT__ENABLED=false`), run it with `E2E_SESSION_CASE=no-jwt`: the spec
  then fails when the API reports JWT on after all. The starter's CI does that in the job `e2e-auth`, after the cookie
  suite.

## Check it

```bash
pnpm run check
```

With an API without JWT: sign in, end the session on the API (or let it expire), reload `/app` and open
"Sicherheit". The browser lands on the login, and after signing in again it returns to the security page.
