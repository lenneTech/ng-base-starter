## ng-base: npm or vendor mode

The app gets [`@lenne.tech/ng-base`](https://github.com/lenneTech/ng-base) in one of two ways:

- **npm mode** (default): ng-base is a dependency, pinned exactly in `package.json`.
- **vendor mode:** the library is copied into `src/core/` as project code, without an npm dependency. `tsconfig.json`
  maps every entry point (`@lenne.tech/ng-base`, `@lenne.tech/ng-base/auth/provide` and so on) to `src/core/`, so
  imports look the same in both modes. `src/core/VENDOR.md` marks the mode and records local changes.

In vendor mode, change `src/core/` only for fixes every ng-base user needs, and send them upstream. Project code stays
outside `src/core/`. The lenne.tech Claude Code plugin has commands to sync a vendored core from upstream and to
prepare local changes as upstream pull requests.

What the app takes from ng-base:

| Entry point                                  | Used for                                                                                      |
| -------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `@lenne.tech/ng-base`                        | Runtime configuration (`LT_RUNTIME_CONFIG`), API URLs (`LtApiUrlService`)                     |
| `@lenne.tech/ng-base/auth`, `…/auth/provide` | Better Auth client and session; the guards `ltAuthGuard`, `ltRoleGuard`, `ltSystemSetupGuard` |
| `@lenne.tech/ng-base/ui`                     | Components, toasts, dialogs, color mode, styles                                               |
| `@lenne.tech/ng-base/ai`                     | The AI assistant, its settings and admin pages                                                |
| `@lenne.tech/ng-base/server`                 | Request handler with the `NG_*` configuration, security headers, API proxy, build identity    |
| `@lenne.tech/ng-base/bug`, `…/bug/server`    | The bug.lt reporter and its `POST /_bug-lt/report` endpoint                                   |

## The backend contract

The app is built against [nest-server-starter](https://github.com/lenneTech/nest-server-starter), the same API
nuxt-base-starter uses.

- **Ports:** API 3000, app 3001. The API's local defaults trust exactly `http://localhost:3001`; another port fails
  2FA and passkeys with `403 INVALID_ORIGIN`, unless the API gets `APP_URL`/`BASE_URL` (as under `lt dev up`).
- **Auth** runs through Better Auth under `/iam/*`. `GET /iam/features` tells the app what the API offers: sign-up,
  e-mail verification, social providers, resend cooldowns. The pages follow it instead of assuming.
- **First admin:** `GET /system-setup/status` and `POST /system-setup/init`. While the API has no user and allows
  the setup over HTTP (locally it does), every page sends visitors to `/auth/setup`. Otherwise `/auth/setup` shows how
  to create the first admin through the API's environment.
- **AI pages** appear only while the API runs its AI module (`GET /ai/status`).

## The generated API client

`pnpm run generate-types` writes `src/api-client/` from the API's OpenAPI document (`${NG_API_URL}/api-docs-json`).
It takes the URL from the shell's `NG_API_URL` or from `.lt-dev/.env` of the monorepo, never guesses a port, and
refuses a URL that belongs to another `lt dev` project.

- Backend types come only from `src/api-client/types.gen.ts`, never written by hand.
- GET requests use the generated `…Resource()` functions; they stay idle without an options factory
  (`xResource(() => ({}))`).
- Mutations use the SDK or the `…Request()` functions.

## Versions

The starter carries the version of the ng-base it pins: starter 22.1.3 is the template for ng-base 22.1.3, and every
ng-base release gets a starter release with the same number. The major is the Angular major.

A generated project has a version of its own and updates ng-base on its own schedule. The migration guides of the
starter, named after the version they lead to, are in
[`migration-guides/`](https://github.com/lenneTech/ng-base-starter/tree/main/migration-guides).
