## Runtime configuration

Everything is set at runtime through `NG_*` environment variables. The SSR server reads them per request and writes
the public half into every HTML response. Nothing is baked into the bundle, so one image runs on every stage.

In code, read the values through `inject(LT_RUNTIME_CONFIG)` from `@lenne.tech/ng-base`; API URLs come from
`LtApiUrlService`. Never read `process.env` in app code, and never add Angular `environment.ts` files.

`.env.example` lists every variable with its meaning. `pnpm run dev` loads `.env`; the built server does not read it,
a deployed stage sets the variables on the container.

| Variable                                                             | Scope           | Meaning                                                                                          |
| -------------------------------------------------------------------- | --------------- | ------------------------------------------------------------------------------------------------ |
| `NG_PUBLIC_SITE_URL`                                                 | public          | Canonical URL, origin of the links in auth mails, extra allowed SSR host. Required in production |
| `NG_PUBLIC_API_URL` / `NG_API_URL`                                   | public / server | The API as the browser reaches it / as the SSR server reaches it                                 |
| `NG_PUBLIC_API_PROXY`                                                | public          | Browser calls go through `/api` on the dev server (local mode without `lt dev up`)               |
| `NG_PUBLIC_APP_ENV`                                                  | public          | Stage: `local`, `develop`, `test` or `production`. Anything but `production` is noindex          |
| `NG_PUBLIC_APP_COMMIT`                                               | public          | Build identity shown under `/app/admin/system` (the image sets it from `APP_VERSION_COMMIT`)     |
| `NG_PUBLIC_STORAGE_PREFIX`, `NG_PUBLIC_COOKIE_PREFIX`                | public          | Storage namespace; the backend's cookie prefix, if it sets one                                   |
| `NG_PUBLIC_PLAUSIBLE_API_HOST`                                       | public          | Analytics host; empty means no tracker at all                                                    |
| `NG_PUBLIC_AUTH_SILENT_PROVIDER`                                     | public          | Social provider for the silent sign-in on the login page; empty means off                        |
| `NG_ALLOWED_HOSTS`                                                   | server          | Extra host names the SSR engine accepts (Angular answers 400 to any other `Host`)                |
| `NG_TRUST_PROXY_HEADERS`                                             | server          | Proxy headers SSR trusts, default `x-forwarded-host,x-forwarded-proto`                           |
| `NG_PUBLIC_LT_BUG_ENABLED`                                           | public          | bug.lt reporter on or off; by default on outside production                                      |
| `NG_LINEAR_API_KEY`, `NG_LINEAR_TEAM_NAME`, `NG_LINEAR_PROJECT_NAME` | server          | Linear target of the bug reports                                                                 |

## Production

At least:

```bash
NG_PUBLIC_SITE_URL=https://example.com
NG_PUBLIC_API_URL=https://api.example.com
NG_API_URL=http://api:3000          # how the SSR server reaches the API
NG_PUBLIC_APP_ENV=production
```

## Bug reports

On every stage but production the bug.lt reporter is on: a "Fehler melden" button that files a report with screenshot
and recent console and network activity in Linear. It needs the Linear values on the server (`NG_LINEAR_API_KEY`,
`NG_LINEAR_TEAM_NAME`, `NG_LINEAR_PROJECT_NAME`). `NG_PUBLIC_LT_BUG_ENABLED=true|false` overrides the stage rule, and
`NG_PUBLIC_LT_BUG_*` adjusts the button. Without `NG_PUBLIC_APP_ENV` it stays off.

## Sign-in through a social provider (SSO)

1. Configure the provider in the API: `betterAuth.socialProviders.<id>` in nest-server, for example `microsoft` with
   client id, client secret, tenant id and `disableProfilePhoto: true`.
2. Register `<API URL>/iam/callback/<id>` as redirect URI at the provider, and add the app origin to the API's
   `trustedOrigins`.
3. `GET /iam/features` then lists the provider, and the login page shows a button "Mit `<Name>` anmelden".
   `/auth/callback` finishes the sign-in.

Use nest-server 12.10.1 or later. Older versions drop the tenant id without a warning, and Microsoft then admits
accounts of every organization.

With `NG_PUBLIC_AUTH_SILENT_PROVIDER=<id>` the login page also tries once per tab to take over an existing provider
session without showing anything. Without a provider session the form stays, without a message. After "Abmelden" no
tab of the browser signs in silently until the next completed sign-in. The provider's own error text never reaches
the page.

## No self sign-up

Deleting the registration page (`src/app/auth/register-page.*` and its route) removes the form, not the endpoint:
`POST /iam/sign-up/email` stays open, and anybody can create an account with a plain request. A project without self
sign-up sets `betterAuth.emailAndPassword.disableSignUp: true` in the API's config (from nest-server 12.3.0 this also
covers social providers). `GET /iam/features` then reports `signUpEnabled: false`, the login page hides its
"Registrieren" link, and `/auth/register` sends visitors to the login, so the page can stay.

## Sign-in through providers alone

With `betterAuth.emailAndPassword.enabled: false` in the API (nest-server 12.11.0 or later), `GET /iam/features`
reports `emailAndPassword: false`. Such an API also reports `passkey: false` and `twoFactor: false`, unless it keeps a
factor on deliberately. The login page then offers only the provider buttons:

- no form, no "Passwort vergessen?" and no "Registrieren";
- the passkey button only while `passkey` is not `false`;
- "Anmeldung nicht möglich" when no method is left, instead of an empty card.

`/auth/register` sends visitors to the login. With sign-up open, the account comes with the first sign-in through a
provider. An API before 12.11.0 does not report the field, and the form stays.

The other pages follow the same answer, again only on an explicit `false`:

| Page                     | Field              | With `false`                                                                                    |
| ------------------------ | ------------------ | ----------------------------------------------------------------------------------------------- |
| `/auth/forgot-password`  | `emailAndPassword` | goes to the login with a toast, replacing the history entry, as `/auth/register`                |
| `/app/settings/security` | `twoFactor`        | no two-factor section                                                                           |
| `/app/settings/security` | `passkey`          | no passkey section and no passkey list request; with neither section left, a hint               |
| `/auth/login?error=…`    | `emailAndPassword` | `account_not_linked` points at the provider used before or the administration, not "wie bisher" |
| `/auth/setup`            | `emailAndPassword` | the form stays (`POST /system-setup/init` wants a password), with a hint how the admin signs in |

**The first admin of a provider-only API.** The system setup still wants a password, and nobody signs in with it. The
admin signs in through a provider whose account carries the same address. Better Auth 1.7 links that account to the
admin on the first sign-in only when the provider reports the address as verified, and the admin's own address is
verified, which the system setup sets. GitHub reports the verified flag of the address. Microsoft Entra ID reports it
only with the optional ID token claim `verified_primary_email`: add it in the app registration under "Token
configuration" → "Add optional claim" → ID. Without it the admin's first sign-in ends with `account_not_linked`.

Do not list the provider in `betterAuth.options.account.accountLinking.trustedProviders` to get there. It skips the
provider's check: Better Auth then links whatever address the provider names, verified or not, and an Entra tenant
admin who sets a user's `mail` to the admin's address signs in as the admin ("nOAuth"). `emailVerified: true` from a provider's
`mapProfileToUser` opens the same gap: Better Auth spreads that result over the provider's own check
(`microsoft-entra-id.mjs`, better-auth 1.7).

The password the system setup asks for is a dormant credential: it does nothing while e-mail and password are off, and
signs the admin in once they are switched on. Take a long random value and do not keep it (nest-server's better-auth
README, "The first administrator").
